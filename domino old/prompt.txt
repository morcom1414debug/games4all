# งาน: สร้างเกม DOMINO Online โดยใช้เกม UNO ต้นแบบเป็นแม่แบบระบบ

ฉันจะแนบไฟล์เกม UNO ต้นแบบให้คุณ ได้แก่ไฟล์ HTML, CSS และ JavaScript

งานของคุณคือสร้างเกม DOMINO Online ใหม่ โดยต้องใช้เกม UNO ที่แนบมาเป็น **แม่แบบหลักของระบบและสถาปัตยกรรม**

## คำสั่งสำคัญที่สุด

ให้ศึกษาและยึดแนวทางจากเกม UNO ต้นแบบ โดยเฉพาะเรื่องต่อไปนี้:

* การเชื่อมต่อระหว่างผู้เล่น

* ระบบ Bot

# กฎเหล็กสูงสุด

## 1. ต้องศึกษาไฟล์ UNO ต้นแบบก่อนเริ่มเขียน

ก่อนสร้างเกม DOMINO ให้ตรวจสอบไฟล์ UNO ที่แนบมาทั้งหมดก่อน

ต้องเข้าใจว่า UNO ต้นแบบทำงานอย่างไรในเรื่อง:

* Firebase
* Peer.js
* Host
* Client
* Room
* Lobby
* Bot
* การ Synchronize ข้อมูล
* aria-live
* Focus
* Disabled Button
* Responsive Layout

ห้ามเดาโครงสร้างเองโดยไม่ตรวจสอบไฟล์ต้นแบบ

---

## 2. ระบบ Multiplayer ต้องใช้แนวทางเดียวกับ UNO ต้นแบบ

DOMINO Online ต้องรักษาแนวคิดสถาปัตยกรรม Multiplayer ของ UNO ต้นแบบ

โดยเฉพาะ:

### Firebase

Firebase ใช้สำหรับ:

* รายการห้อง
* สถานะห้อง
* จำนวนผู้เล่น
* สถานะว่าห้องกำลังรอหรือเริ่มเกมแล้ว
* Host Peer ID
* การตรวจสอบห้องที่ยังใช้งานอยู่
* การอัปเดตสถานะห้อง
* การลบห้อง

ห้ามเปลี่ยนแนวทาง Firebase โดยไม่จำเป็น

ให้สร้าง namespace หรือ path สำหรับเกม DOMINO แยกจาก UNO อย่างชัดเจน

ตัวอย่างแนวคิด:

* UNO ใช้ข้อมูลของ UNO
* DOMINO ต้องใช้ข้อมูลของ DOMINO

ห้ามให้ห้องของ UNO และ DOMINO ปะปนกัน

---

## 3. Peer.js ต้องใช้แนวทางเดียวกับ UNO ต้นแบบ

Peer.js ใช้สำหรับ Multiplayer แบบ Real-time ระหว่าง:

* Host
* Client

ให้คงแนวทาง:

* Host เป็นผู้ควบคุม Game State หลัก
* Client ส่ง Action ไปยัง Host
* Host ตรวจสอบ Action
* Host อัปเดต Game State
* Host Broadcast State กลับไปยังผู้เล่น

ห้ามให้ Client สามารถแก้ไข Game State หลักเองโดยอิสระ

Host ต้องเป็นผู้มีอำนาจหลักในการตัดสิน:

* การวางโดมิโน่
* การจั่ว
* การใช้โดมิโน่พิเศษ
* การเปลี่ยน Turn
* การข้าม Turn
* การกลับทิศทาง
* คะแนน
* การลงโทษ DOMINO!
* การจบเกม

# Accessibility เป็นกฎเหล็กระดับสูงสุด

เกมนี้ต้องสามารถเล่นได้ครบ 100% สำหรับผู้เล่นตาบอด

ต้องรองรับ:

* NVDA
* JAWS
* VoiceOver
* Keyboard Navigation
* Touch Screen Reader

ห้ามสร้างเกมที่ผู้เล่นต้องพึ่งพาการมองเห็นเพื่อเล่น

ทุกข้อมูลสำคัญต้องเข้าถึงได้ด้วย Screen Reader

---

# ระบบ aria-live

ให้ใช้แนวทางเดียวกับ UNO ต้นแบบ

ต้องมีพื้นที่ประกาศอย่างน้อย:

* aria-live="polite"
* aria-live="assertive"

Visual Animation ต้องไม่รบกวน Screen Reader

Animation ที่เป็นเพียงภาพต้อง:

* ไม่ถูกอ่านซ้ำ
* ใช้ aria-hidden เมื่อเหมาะสม

ข้อความสำคัญต้องประกาศผ่าน aria-live

ตัวอย่าง:

* ถึงรอบของ สมชาย
* สมชาย วาง 7 กับ 4
* บอทมาริโอ้ ใช้ หลับ
* บอทมาริโอ้ ใช้ 2+
* คุณจั่วโดมิโน่ 1 ตัว
* คุณถูกบังคับให้จั่ว 3 ตัว
* ทิศทางการเล่นกลับแล้ว
* คุณต้องกด DOMINO!
* คุณลืมกด DOMINO! ถูกลงโทษ จั่วเพิ่ม 2 ตัว
* คุณยังสามารถเล่นต่อได้
* ไม่มีโดมิโน่ที่วางได้ ระบบเปลี่ยนไปยังผู้เล่นถัดไป
* สมชายชนะรอบนี้

ต้องมีระบบป้องกัน aria-live ประกาศข้อความซ้อนกันมากเกินไป

หาก UNO ต้นแบบมีระบบ Queue สำหรับ aria-live ให้รักษาแนวคิดเดียวกัน

---

# Focus Management

ต้องใช้แนวทางเดียวกับ UNO ต้นแบบ

เมื่อเปลี่ยนหน้าจอ:

* Focus ต้องย้ายไปยัง Heading หรือ Element สำคัญของหน้าจอนั้น

ตัวอย่าง:

หน้า Lobby:

Focus ไปที่ Heading Lobby

หน้าเกม:

Focus ต้องไม่กระโดดมั่ว

หน้าผลการแข่งขัน:

Focus ไปที่ Heading ผลการแข่งขัน

หน้าคู่มือ:

Focus ไปที่ Heading คู่มือ

ห้ามใช้ Auto Focus ที่ทำให้ผู้ใช้ Screen Reader ถูกขัดจังหวะระหว่างเล่นเกมโดยไม่จำเป็น

---

# Button Lock / Disabled / Dim

ต้องใช้แนวทางเดียวกับ UNO ต้นแบบ

เมื่อปุ่มไม่สามารถใช้งานได้:

* ต้อง Disabled จริง
* ไม่ใช่เพียงเปลี่ยนสี
* ต้องไม่สามารถกดด้วย Keyboard
* ต้องมีภาพ Dim หรือ Disabled State ที่ชัดเจน

ห้ามทำปุ่มที่ดูเหมือน Disabled แต่ยังสามารถกดได้

ตัวอย่าง:

## หน้าแรก

หากยังไม่กรอกชื่อ:

ปุ่มยืนยันต้อง:

* disabled
* dim
* กดไม่ได้

เมื่อกรอกชื่อแล้ว:

* enabled
* กดได้

---

# หน้าแรก

หน้าแรกประกอบด้วย:

* ปุ่มกลับสู่ชุมชน
* ชื่อเกม
* คำอธิบายเกม
* ช่องกรอกชื่อเล่น
* ปุ่มยืนยัน

## การกรอกชื่อ

ผู้เล่นต้องกรอกชื่อก่อนเข้าสู่ Lobby

หากยังไม่มีชื่อ:

ปุ่มยืนยันต้อง Disabled

เมื่อกรอกชื่อ:

ปุ่มยืนยันจึง Enabled

ต้องมี aria-label ที่เหมาะสมสำหรับช่องกรอกชื่อ

ชื่อผู้เล่นต้องถูกนำไปใช้ใน:

* Lobby
* รายชื่อผู้เล่น
* สถานะผู้เล่น
* Turn
* Event
* คะแนน
* ผลการแข่งขัน

---

# Lobby

ใช้แนวทางและ Flow เดียวกับ UNO ต้นแบบ

Lobby ต้องมี:

* สร้างห้อง
* รายการห้องที่เปิดอยู่
* เข้าร่วมห้อง
* คู่มือการเล่น

หาก UNO ต้นแบบมีการ Refresh รายการห้องแบบ Real-time ให้ใช้แนวทางเดียวกัน

---

# ระบบสร้างห้อง

เมื่อผู้เล่นสร้างห้อง:

* ต้องสร้าง Room ID
* ต้องบันทึกข้อมูลห้องใน Firebase
* ต้องกำหนด Host
* ต้องเข้าสู่ Lobby
* ต้องแสดง Room ID
* ต้องแสดงรายชื่อผู้เล่น

Host ต้องสามารถ:

* เพิ่ม Bot
* ลด Bot
* เริ่มเกม

Client:

* ไม่สามารถเพิ่ม Bot
* ไม่สามารถลด Bot
* ไม่สามารถเริ่มเกม

ปุ่ม Host Control ต้อง:

* ซ่อนจาก Client หรือ Disabled ตามแนวทาง UNO ต้นแบบ

---

# ระบบเข้าร่วมห้อง

ผู้เล่นต้องสามารถ:

* ดูรายการห้อง
* ฟังข้อมูลห้องผ่าน Screen Reader
* เลือกปุ่มเข้าร่วมห้อง

aria-label ควรบอกข้อมูลอย่างชัดเจน เช่น:

"เข้าร่วมห้อง domino00001 มีผู้เล่น 3 จาก 6 คน"

เมื่อกำลังเชื่อมต่อ:

* ป้องกันการกดซ้ำ
* Disable ปุ่ม
* Dim ปุ่ม
* ประกาศผ่าน aria-live

ตัวอย่าง:

"กำลังเชื่อมต่อไปยัง Host"

หากเชื่อมต่อไม่สำเร็จ:

* แจ้งผ่าน aria-live
* กลับสู่สถานะที่เหมาะสม
* ปลดล็อกปุ่มที่ควรกลับมาใช้งานได้

# ตัวละครและผู้เล่น

ยกเลิกระบบสีประจำตัวละครของ UNO

DOMINO ใช้:

* ชื่อผู้เล่น

ผู้เล่นทุกคนต้องมี:

* id
* name

* score
* จำนวนโดมิโน่ในมือ

ห้ามใช้สีเป็นตัวตนหลักของผู้เล่น

* บอทซุปเปอร์แมน
* บอทแมงมุม
* บอทมาริโอ้
* บอทนารูโตะ
* บอทโซนิค
* บอทปิกาจู
* บอทเบ็นเท็น
* บอทโดราเอมอน
* บอทลูฟี่
* บอทคิริโตะ

## กฎชื่อ

ห้ามชื่อซ้ำภายในห้องเดียวกัน

ทั้ง:

* ผู้เล่นจริง
* Bot

ต้องไม่มีชื่อซ้ำ

หากเพิ่ม Bot:

ต้องสุ่มจากชื่อที่ยังไม่ได้ใช้งาน

# เป้าหมายเกม

ผู้เล่นคนใดมีคะแนนสะสมถึง:

200 คะแนน

ก่อน ถือเป็นผู้ชนะเกม

ระบบคะแนนต้อง:

* แสดงคะแนนของทุกคน
* Sync คะแนนให้ทุก Client
* แสดงผลการแข่งขันอย่างถูกต้อง

---

# กระดานเกม

ด้านบนของหน้าจอ

แสดงสถานะผู้เล่นทุกคน

แต่ละคนแสดง:

* Avatar แนวโดมิโน่น่ารัก
* ชื่อ
* คะแนน
* จำนวนโดมิโน่คงเหลือ

Visual Avatar เป็นเพียงข้อมูลตกแต่ง

ต้องไม่เป็นข้อมูลสำคัญเพียงอย่างเดียว

Screen Reader ต้องสามารถทราบ:

* ชื่อ
* คะแนน
* จำนวนโดมิโน่

---

# Heading สถานะ Turn

ใต้แถบสถานะผู้เล่น

ต้องมี Heading

ตัวอย่าง:

"รอบของ สมชาย"

หรือ:

"รอบของ บอทมาริโอ้"

Heading ต้องเป็นข้อมูลที่ Screen Reader เข้าถึงได้

เมื่อ Turn เปลี่ยน:

ต้องประกาศผ่าน aria-live

---

# Event ล่าสุด

ใต้หรือใกล้กับ Heading

มีพื้นที่แสดง Event ล่าสุด

ตัวอย่าง:

* ซุปเปอร์แมน ใช้ 2+
* แมงมุม จั่ว 2 ตัว และถูกข้ามตา
* นารูโตะ ใช้ ย้อนศร
* สมชาย วาง 7 กับ 4
* บอทโซนิค ประกาศ DOMINO!

Event ล่าสุดต้อง:

* แสดงบนหน้าจอ
* ประกาศผ่าน aria-live

แต่ต้องป้องกันข้อความประกาศซ้ำโดยไม่จำเป็น

# กฎการวางโดมิโน่

การวางต้องตรวจสอบกับ:

* ปลายซ้าย
* ปลายขวา

โดมิโน่สามารถวางได้เมื่อเลขด้านใดด้านหนึ่งตรงกับปลายที่ต้องการต่อ

ระบบต้องตรวจสอบความถูกต้องจาก Host

ห้ามเชื่อข้อมูลจาก Client โดยตรงโดยไม่ตรวจสอบ

---

# การจั่วอัตโนมัติ

หากผู้เล่นไม่มีโดมิโน่ที่สามารถวางได้

ระบบต้อง:

1. จั่วโดมิโน่ 1 ตัว
2. ตรวจสอบอีกครั้ง
3. หากยังไม่มีตัวที่วางได้ ให้จั่วอีก 1 ตัว
4. ทำต่อไปทีละ 1 ตัว

หยุดเมื่อ:

* พบโดมิโน่ที่สามารถวางได้
* หรือกองจั่วหมด

---

## สำคัญ

ไม่มีปุ่มจั่วในเกม DOMINO

การจั่วเป็นระบบอัตโนมัติ

เมื่อจั่ว:

ต้องประกาศผ่าน aria-live

ตัวอย่าง:

"คุณไม่มีโดมิโน่ที่วางได้ ระบบกำลังจั่ว"

"คุณจั่วโดมิโน่ 1 ตัว และสามารถวางได้แล้ว"

หรือ:

"คุณจั่วโดมิโน่ 5 ตัว แต่ยังไม่มีตัวที่วางได้"

---

# กฎ DOMINO!

ด้านล่างสุดของหน้าจอ

ต้องมีปุ่ม:

DOMINO!

---

## เงื่อนไข

เมื่อผู้เล่นเหลือโดมิโน่:

2 ตัว

และมีอย่างน้อย:

1 ตัวที่สามารถวางได้

ผู้เล่นต้องกด:

DOMINO!

ก่อน

จึงจะสามารถวางโดมิโน่ตัวรองสุดท้ายได้

---

## หากกด DOMINO!

ระบบต้อง:

* บันทึกสถานะว่าได้ประกาศแล้ว
* ประกาศผ่าน aria-live
* ปลดล็อกการวางโดมิโน่ตัวรองสุดท้าย

---

## หากลืมกด

หากผู้เล่นวางโดมิโน่จนเหลือ:

1 ตัว

โดยไม่ได้ประกาศ DOMINO!

ต้อง:

* ถูกลงโทษทันที
* จั่วเพิ่ม 2 ตัว
* Sync Game State
* ประกาศผ่าน aria-live

ตัวอย่าง:

"คุณลืมกด DOMINO! ถูกลงโทษ จั่วเพิ่ม 2 ตัว"

---

## Bot

Bot ต้องใช้กฎเดียวกัน

เมื่อ Bot เหลือ 2 ตัวและเข้าเงื่อนไข:

Bot ต้องประกาศ DOMINO! อัตโนมัติ

และประกาศ Event เช่น:

"บอทมาริโอ้ ประกาศ DOMINO!"

---

# การเล่นต่อหลังวางโดมิโน่

หลังจากวางโดมิโน่ทุกครั้ง

ระบบต้องตรวจสอบทันทีว่า

ผู้เล่นคนเดิมยังมีโดมิโน่ที่สามารถต่อจากปลายปัจจุบันได้หรือไม่

---

## หากยังมีตัวที่เล่นได้

ผู้เล่น:

ยังเล่นต่อได้

ยังไม่เปลี่ยน Turn

ต้องประกาศหรือแสดงข้อความที่เหมาะสม เช่น:

"คุณยังมีโดมิโน่ที่สามารถเล่นต่อได้"

---

## หากไม่มีตัวเล่นต่อ

ระบบต้อง:

* รอประมาณ 700 ถึง 1000ms
* เปลี่ยน Turn อัตโนมัติ

ไปยังผู้เล่นถัดไป

---

## กฎนี้ใช้กับ

* ผู้เล่นจริง
* Bot

เหมือนกัน

# Bot Logic

Bot ต้องเล่นผ่าน Game Logic เดียวกับผู้เล่น

ห้ามสร้างกฎพิเศษให้ Bot ที่ต่างจากผู้เล่น

Bot ต้อง:

1. ตรวจสอบโดมิโน่ที่เล่นได้
2. เลือกโดมิโน่ที่สามารถวางได้
3. วางตามกฎ
4. ตรวจสอบ DOMINO!
5. เล่นต่อหากยังสามารถเล่นได้
6. เปลี่ยน Turn เมื่อเล่นต่อไม่ได้
7. จั่วอัตโนมัติเมื่อไม่มีตัววางได้

Bot Action ทั้งหมดต้องผ่าน Host

Client ไม่ควรประมวลผล Bot Logic แยกกันจนเกิดความไม่ตรงกันของ Game State

---

# การ Synchronize Game State

ให้ใช้แนวทาง Host Authority แบบ UNO ต้นแบบ

Host เป็นผู้เก็บข้อมูลจริงของ:

* deck
* left end
* right end
* players
* hands
* scores
* turnIndex
* direction
* DOMINO status
* game status

Client ได้รับข้อมูลที่จำเป็นสำหรับการแสดงผลและการเล่นของตนเอง

---

# ความปลอดภัยของข้อมูลผู้เล่น

Client ต้องไม่สามารถเห็นโดมิโน่ในมือของผู้เล่นคนอื่นโดยไม่จำเป็น

แต่ต้องสามารถเห็น:

* ชื่อผู้เล่น
* คะแนน
* จำนวนโดมิโน่คงเหลือ
* สถานะ Turn

มือของผู้เล่นแต่ละคนต้องเป็นข้อมูลส่วนตัวตามแนวทาง Multiplayer ของ UNO ต้นแบบ

---

# การล็อกการควบคุมระหว่าง Turn

เมื่อไม่ใช่ Turn ของผู้เล่น:

โดมิโน่ในมือที่เป็นปุ่มต้อง:

* Disabled หรือไม่สามารถ Action ได้ตามแนวทางที่เหมาะสมของ UNO ต้นแบบ
* มี Visual State ที่ชัดเจน
* ไม่สามารถส่ง Action ผิด Turn

เมื่อถึง Turn ของผู้เล่น:

เฉพาะโดมิโน่ที่สามารถเล่นได้ต้องพร้อมใช้งาน

โดมิโน่ที่เล่นไม่ได้ต้อง:

* Dim
* มีสถานะ Disabled ที่ชัดเจน
* ไม่สามารถวางได้

แต่ Screen Reader ยังต้องสามารถทราบข้อมูลโดมิโน่ในมือได้อย่างเหมาะสม

# ตรวจสอบก่อนส่งงาน

ก่อนส่งงาน ต้องตรวจสอบทุกหัวข้อดังต่อไปนี้

## Multiplayer

* สร้างห้องได้
* รายการห้องแสดงถูกต้อง
* เข้าร่วมห้องได้
* Host ทำงานถูกต้อง
* Client ทำงานถูกต้อง
* Bot Sync ถูกต้อง
* ผู้เล่นออกจากห้องได้
* Host ออกจากห้องแล้วห้องถูกจัดการถูกต้อง
* ห้องเต็มเข้าร่วมไม่ได้

## Firebase

* ห้อง DOMINO แยกจาก UNO
* ข้อมูลห้องไม่ปะปนกับเกมอื่น
* สถานะห้องอัปเดตถูกต้อง
* ห้องเก่าถูกจัดการตามแนวทางต้นแบบ

## Peer.js

* Client เชื่อมต่อ Host ได้
* Action ถูกส่งไปยัง Host
* Host ตรวจสอบ Action
* Game State Sync ถูกต้อง

## Accessibility

* aria-label ครบ
* aria-live ทำงาน
* polite และ assertive ใช้อย่างเหมาะสม
* ไม่มีข้อความสำคัญที่เห็นได้อย่างเดียว
* Keyboard ใช้งานได้
* Focus ถูกต้อง
* Disabled Button ถูกต้อง
* Dim State ชัดเจน
* Screen Reader เล่นได้ครบ

## DOMINO!

* กดได้เฉพาะเมื่อเข้าเงื่อนไข
* ผู้เล่นต้องประกาศก่อนวางตัวรองสุดท้าย
* ลืมแล้วถูกลงโทษ 2 ตัว
* Bot ใช้กฎเดียวกัน

## Game Logic

* วางซ้ายได้
* วางขวาได้
* Special Domino ทำงานถูกต้อง
* 2+ ทำงานถูกต้อง
* 3+ ทำงานถูกต้อง
* หลับทำงานถูกต้อง
* ย้อนศรทำงานถูกต้อง
* เล่นต่อใน Turn เดียวกันได้
* Auto Draw ทำงานถูกต้อง

ห้ามเปลี่ยนสถาปัตยกรรม Multiplayer ของ UNO ต้นแบบโดยไม่จำเป็น

ห้ามลดระดับ Accessibility

ห้ามตัด:

* aria-live
* aria-label
* Focus Management
* Disabled State
* Dim State
* Keyboard Accessibility
* Firebase
* Peer.js
* Host/Client Architecture

เพียงเพราะต้องการเขียนโค้ดให้สั้นลง

ให้สร้างเกม DOMINO ใหม่โดยใช้ UNO ต้นแบบเป็นแม่แบบหลักของระบบ

แต่เปลี่ยน:

* กติกา UNO
* การ์ด UNO
* สีประจำตัวละคร

ให้กลายเป็น:

* ระบบ DOMINO
* กฎ DOMINO ตามที่กำหนด
* ชื่อผู้เล่นและชื่อ Bot

ทุกระบบที่เกี่ยวข้องกับ:

Lobby,
Room,
Multiplayer,
Firebase,
Peer.js,
Host,
Client,
Bot,
Accessibility,
aria-live,
aria-label,
Focus,
Disabled,
Dim,
Responsive
